# Диагностика пространственного звука

2026-10-21: пользователь также сообщает дребезг звука стационарного MG42
при непрерывной стрельбе. Это отдельное воспроизведение, не доказанное
следствие широкой центральной зоны. Проверить короткую/долгую очередь,
повторяющиеся PCM-блоки, XMA ring output-valid, callback spacing/underruns
и clipping при наложении выстрелов. Референсный patch 0061 — кандидат,
а не установленное исправление. Игровой микс пока не записан; код не менялся.

Уточнение: Island и Night Drop, по наблюдению пользователя любой стационарный
MG42. Звук кажется зацикленным, и на стыках повторов возникает короткое
подвисание. Время начала и длительность не измерены. Для A/B сравнения
нужна непрерывная очередь у одного пулемёта, запись до/после XMA и выхода,
сопоставление границ цикла с callback intervals и PCM continuity. Не объявлять
причиной XMA restart, loop metadata или нехватку CPU без такой проверки.

Read-only inventory наших global/Island/Night Drop NSLB-банков внешним
tools/x360_family/nslb.py подтвердил отдельный стерео XMA звук стрельбы
MG42 от первого лица, помеченный loop, длиной около 0.78 s, и отдельный хвост
последнего выстрела. Это конкретный кандидат для записи периодического стыка,
не доказательство выбранной игрой волны в каждом эпизоде. Полный вывод с
игровыми метаданными сохранён только в ignored reports/mg42-bank-inventory.txt.

Ghidra по нашему XEX подтвердил границы 0x823B80A8 (pump) и 0x823B7ED8
(reset). Pump при равных read/write offsets и output-valid=0 возвращает
полный блок 0x800 bytes; import registry сопоставляет 0x82578DCC с
XMAIsOutputBufferValid, 0x82578DDC/0x82578DEC с Write/ReadOffset.
Это подтверждает зависимость исходного читателя от семантики кольца,
описанную во внешнем аудиореференсе. Лог logs/ghidra-mg42-xma-pump.log
остаётся private. Пока нет runtime-трассы, связывающей эту ветку с каждым
слышимым стыком, поэтому patch 0061 не объявлен принятым исправлением.

2026-10-21, уточнение пользователя в текущем запуске: наушники, обычная
реплика солдата рядом (не рация). У левого края экрана голос воспринимается
почти по центру; если повернуться дальше и оставить солдата строго слева
за экраном, голос заметно переходит в левое ухо. Перестановка сторон в этой
проверке не подтверждается. Рабочее описание — широкая центральная зона,
а не установленная ошибка L/R или полностью монофонический вывод.

Проверена фактическая SIMD-конверсия pinned SDK conversion.h отдельным
нативным probe: 256 знакопеременных BE float samples в каждом из шести
каналов по очереди. FL/BL выходят только слева, FR/BR только справа,
FC поровну в оба уха, LFE не попадает в stereo. Все шесть проверок прошли;
конвертер не объединяет боковые каналы в центр сам по себе. Это проверка
математики сведения, не доказательство корректного панорамирования речи
в настоящем игровом миксе. Private helper reports/audio-conversion-probe.cpp,
логи logs/audio-conversion-probe-build.log и logs/audio-conversion-probe.log.
Команды: Enter-Toolchain.ps1; cl /std:c++latest /EHsc /O2 /DNDEBUG
/Iexternal/rexglue-sdk/include reports/audio-conversion-probe.cpp (выходы
в ignored reports/); запуск audio-conversion-probe.exe.

Ghidra по нашему SP XEX E057FFCD129AF913B9C7334C847F749115FA6A4E3C0A9EDACDD2DB728F003682
подтвердил SoundHandle position 0x8247D968: (-y,z,x), и передачу конечных
listener vectors через 0x8246BB70 в NSL. Это ещё не проверка всего пути от

функции. Private log logs/ghidra-audio-listener-source.log. Адреса/hook не
менялись. Следующий диагностический шаг — ограниченная запись шести игровых
каналов до сведения и стереорезультата на одной реплике при известном угле,
сопоставленная с listener/source orientation. Не расширять stereo произвольным
усилением разности L-R: причина и расхождение с оригиналом ещё не доказаны.

Текущий запуск native-20261021-092702-382.log сообщает Realtek, 2 канала,
48000 Hz, submitting 2 ch. Это другой endpoint, чем прежняя 8-канальная
Logitech; нельзя приписывать одинаковую причину всем предыдущим наблюдениям.

В нашем pinned SDK StereoFold уже исключает LFE (lfe=0), тогда как SurroundMix
по умолчанию пропускает его (lfe=1). Поэтому чужой приём с отключением LFE
для многоканального выхода не изменит текущий стереовыход и не является
универсальным исправлением неправильного направления. Нужен отдельно
воспроизводимый неподвижный источник и сведения об используемом устройстве.

В XmaContext::Work нашего SDK присутствует проверка output_rb.empty(),
безусловно очищающая output_buffer_valid, в том числе после прохода без
записанного PCM. Внешний patch 0061 ограничивает это фактом записи и
переполнения кольца. Совпадение кода подтверждено; повтор концов звуков в
нашем текущем запуске не измерен. Это отдельный кандидат для проверки XMA,
не объяснение панорамы. Patch 0061 не применён; pacing, SDK ABI и audio drain
при Runtime restart необходимо проверять отдельно перед любым переносом.

native-20261013-130703-196.1.log: endpoint Logitech PRO X Wireless Gaming
Headset сообщает 8 каналов / 48000 Hz; SDK отправляет 6 каналов. Ранее endpoint
Realtek сообщал 2 канала. Настройки виртуального surround гарнитуры не проверены.

Проверенный pinned SDL driver выбирает stereo fold для endpoint <=2 каналов;
для большего количества передаёт 6 каналов в SDL AudioStream, который выполняет
последующее преобразование к endpoint. conversion.h сохраняет guest channel
order FL/FR/FC/LFE/BL/BR в six-channel output; default SurroundMix unity.
Таким образом, восьмиканальный endpoint — конкретная развилка для сравнения,
но сам по себе не доказывает ошибку каналов.

Следующая проверка: один неподвижный источник, повороты камеры по четырём
направлениям, сопоставление front/center/rear каналов и конечного endpoint;
сравнить с двухканальным выходом и оригиналом. Проверить также attenuation
и guest mix до host conversion. Не менять слепо местами каналы и не повышать
общую громкость в качестве исправления позиционирования.
