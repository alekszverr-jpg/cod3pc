## Цель и технические ограничения

Оригинальная одиночная кампания Xbox 360 работает как самостоятельное Windows
x64 приложение: статическая рекомпиляция PPC → C++ → x64, оригинальный движок
и ресурсы принадлежащей пользователю копии. Сохраняем игровую логику, физику,
анимации, графику, звук и сценарии. Интерпретатор, JIT или процесс эмулятора
не становятся backend итогового приложения. Multiplayer вне начального объёма.

Основа — ReXGlue 0.10.0, commit
`c94f5ebdcb3c9d1a460ca48e04f9758448f8d518`, официальный Xenos GPU plugin
с проверяемыми локальными исправлениями совместимости. Используем API исходников
этой версии и фактический CLI `--help`. XenonRecomp/XenosRecomp — возможные
альтернативы только при установленной технической необходимости. CoD3Recomp
служит исследовательским ориентиром; развитие нашего порта не зависит от
ожидания его автора. Заимствование исходников требует проверки лицензии.

VS Code подходит как редактор; необходимые MSVC и Windows SDK предоставляют
установленные Visual Studio Build Tools. Полная IDE не является обязательной.
Xenia может быть эталоном Xbox 360 для локального сравнения. Присланные кадры
RPCS3 помогают сравнить внешний вид, но не доказывают семантику GPU Xbox 360.

## Ближайший приоритет: переход кампании в одном окне и процессе

Исследование 2026-10-16: COD3 Reborn (jxnplays/cod3-recomp) продолжает
CoD3Recomp и тоже использует новый процесс для перехода. Готового исправления
нашего lifecycle там нет. Полезные пункты для дальнейшей работы:

- M6/M7: opt-in проверки загрузки собранных уровней с метриками I/O, кадров,
  draw/triangle counts и отдельными отметками entry/render/control; без заявления
  о проходимости по одному успешному запуску, с изолированными профилями.
- M8/input: возврат захвата после Alt-Tab/настроек, отсутствие поворота после
  остановки мыши, насыщение эмулируемого стика, повторное чтение input в кадре,
  согласованность прицеливания и частоты кадров.
- M8/settings: согласованные video-mode APIs и dirty/apply/save для всех полей;
  optional image controls с неизменным изображением при defaults и проверкой
  точности таблиц/порядка относительно исходной gamma.
- M8/ultrawide: отдельно проверить projection, HUD, меню, видео и viewmodel;
  FSR/XeSS/SSAO/soft shadows из чужого roadmap не считать готовыми решениями.

Приоритеты выше не отменяют текущий блокер потоков. Источники, лицензии и
границы применимости: [JXNPLAYS_REVIEW.md](JXNPLAYS_REVIEW.md).

Требование пользователя 2026-10-15: переход должен быть бесшовным, без
закрытия окна и повторного запуска cod3pc. Проверенный межпроцессный relaunch
остаётся временным сравнительным вариантом, а не окончательным UX.

Уточнение 2026-10-16: дамп старого процесса показал три workers в бесконечном
idle wait. Сейчас проверяется opt-in повторение оригинального wait по 50 ms
с кооперативным выходом. Затем — creation seal и фактический join всех guest
потоков, остановка аудио/XMA без force-kill/abandon, завершение GPU и только
после этих барьеров очистка DLL/корутин и пересоздание Runtime с тем же окном.
Подробности и привязка к инструкциям — SEAMLESS_TRANSITIONS.md.

2026-10-17: первый bounded-wait прогон дал 0 pending, Island подтверждена.
Creation seal и ожидание native exit теперь реализованы в SDK-патче и покрыты
конкурентным тестом; runtime-проверка opt-in TitleThreadDrain ещё ожидается.
После неё приоритет — остановка audio/XMA/GPU без живых callbacks и освобождения
памяти по тайм-ауту, затем очистка и пересоздание Runtime с сохранением окна.

Критерии: один PID и тот же native window до/после Saint-Lo→Island; исходные
664 байта launch data прочитаны оригинальным startup; старые guest/audio/GPU
workers завершены до освобождения памяти; старые DLL/fibers/callbacks не
используются; DoF, ввод, полноэкранный режим и userdata сохраняются. Два
повтора из saint_lo_final без зависания/роста оставшихся потоков, затем Continue
после штатного выхода. Не требуется устранить исходную загрузку ресурсов:
оригинальный loading screen допустим, закрытие приложения — нет.

Найденный технический блокер в pinned SDK: KernelState::TerminateTitle ждёт
200 ms, оставляет straggler threads работающими, удаляет их из map и сбрасывает
termination flag. ReXApp::OnClosing использует _Exit именно из-за небезопасного
teardown при таких потоках. Runtime::Shutdown освобождает GPU/audio/input,
KernelState и память. Нельзя вызывать его на этом пути, пока не доказана
полная остановка всех потребителей. См. SEAMLESS_TRANSITIONS.md.

После этого — стабильность/прохождение Island и подключение следующей DLL.

## Совместимость основных систем

Проверять системы по мере появления в реальном прохождении; дефекты, мешающие
продолжению, имеют приоритет над добавлением следующих уровней.

| Система | Работа и необходимая проверка |
|---|---|
| PPC/runtime | ABI, endian, FPU/VMX128, стек, tail calls, indirect calls, потоки и timing; каждый missing import имеет caller, контракт и осмысленную реализацию |
| Сценарии | Frame/timed/condition/event waits, сохранение PPC и host frames, освобождение fibers, переходы задач и модулей |
| VFS/ресурсы | Оригинальные пути, регистр имён, структура, сигнатуры и зависимости; сохранить исходный loader, не предполагать форматы CoD4 |
| Графика | Buffers, texture tiling/swizzle, shaders, depth/EDRAM/present; сравнивать GPU captures и живой кадр, ограничивать исправление доказанной областью |
| Ввод | Клавиатура/мышь/XInput, чувствительность, движение/прицеливание, переключение устройств, меню и gameplay |
| Звук/видео | Реальные codecs/events, синхронизация, голоса/музыка/эффекты, длительные сцены; audio callback не доказывает правильный звук |
| Gameplay | Оружие, анимации, физика/коллизии, AI, урон, scripted sequences, транспорт и цели миссий |
| Сохранения | Checkpoints, повтор после смерти, рестарт миссии, продолжение после закрытия процесса, переходы кампании |

с символами, а не Debug -O0.

Перед M8: проверить долгие игровые сессии, настройки изображения/звука/ввода,
ошибки отсутствующих ресурсов, понятный запуск и импорт собственной копии,
воспроизводимость сборки и зависимости/лицензии распространяемого пакета.
Оригинальные и производные игровые данные/код не помещать в Git и remote builds.
Распространяемый состав определить после отдельной проверки; не включать
закрытые Xbox SDK, игровые assets, ключи и приватные диагностические материалы.

## Рабочий цикл и команды

Для каждого существенного исправления: точное воспроизведение → первая неверная
операция → проверка оригинального кода/SDK → минимальное исправление → подходящие
tests → strict codegen → native build → реальный повтор проблемного участка.
Фиксировать команды, ошибки, область проверки и следующий блокер в документах.
Generated functions не редактировать вручную. `--force` допустим только для
диагностики и не является критерием готовности; strict запуск использует
`--ignore-stamp`.

```powershell
./tools/Check-Environment.ps1
./tools/Build.ps1 -Stage Tests
./tools/Build.ps1 -Stage Analyze
./tools/Build.ps1 -Stage Codegen
./tools/Build.ps1 -Stage Build
./tools/Run-Native.ps1 -Seconds 0 -Interactive
./tools/Inspect-Target.ps1 -Address 0x823C1F68
```

Ручные проверки начинаются из обычного меню, чтобы продолжать с checkpoint.
Запускать одно окно. -FirstMission применять только для проверки новой миссии,
когда это действительно нужно; пользователь предпочитает продолжение сохранения.

Старые примеры init из исходного промпта заменены командами v0.10.0:
`--project-name`, `--xex-path`, `--project-root`, `cod3pc_manifest.toml`.
Повторно init поверх проекта не выполнять; точный bootstrap приведён в
[BUILDING.md](BUILDING.md). Восемь текущих parser/coverage/native tests
проверяют инструменты и отдельные runtime свойства, а не проходимость кампании.

Продолжать техническую работу автономно в согласованном объёме. Ручные игровые
проверки запрашивать, когда они нужны для подтверждения поведения. Новые
системные разрешения, отсутствующие assets и принципиальная смена подхода
обсуждаются отдельно. Сроки следующего этапа определяются найденными дефектами,
а готовность — перечисленными проверками.
