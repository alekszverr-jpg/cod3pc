## Подход к внешним реализациям (2026-10-20)

Продолжаем собственный порт и используем совместимые решения других проектов.
Не ждём их завершения и не повторяем уже решённые задачи без необходимости.
Перед самостоятельной разработкой общей подсистемы проверяем существующие
исправления ReXGlue и изученные референсы.

- Общие ошибки SDK: проверяем чужой патч на нашем pinned SDK и воспроизведении;
  при подтверждении адаптируем с нужными лицензиями и указанием происхождения.
- Игровые hooks и адреса: сначала подтверждаем инструкции/контракт на нашем
  XEX и его hash, затем переносим подход. Чужие offsets не являются доказательством.
- Большие подсистемы: сравниваем стоимость адаптации, зависимостей, поддержки
  и повторной проверки с небольшой собственной реализацией. Целиком менять
  стек только ради числа чужих функций не требуется.
- Интерфейс/ввод: технический механизм можно заимствовать; результат обязан
  соответствовать критериям полноценной ПК-версии ниже.
- Для каждого переноса записываем URL, ревизию, происхождение и лицензии,
  изменённую область, наши tests и фактическую игровую приёмку. Не переносим
  игровые assets/generated code в Git и не выдаём внешнюю проверку за нашу.

Ближайший порядок: закончить диагностику огоньков, затем проверить внешние
аудио-исправления на нашем пространственном звуке/XMA. Уже принятые сохранения,
same-process переходы, трава и тени остаются обязательными регрессиями.

## Продуктовый ориентир: полноценная ПК-версия (2026-10-20)

Требование пользователя: игра должна выглядеть и управляться так, будто
изначально вышла на ПК. Сохраняем художественный стиль оригинала и развиваем
его главное меню и меню паузы для PC. Этот критерий применяется ко всем
заимствуемым идеям и уточняет прежний пункт о лаунчере/настройках M8.

- Все пользовательские настройки доступны внутри игры: видео (включая
  оконный режим, разрешение, VSync, FOV и DoF), звук и управление.
  Новые страницы/виджеты соответствуют стилю, шрифтам и локализации игры.
  F4/ImGui, консоль, TOML и параметры запуска остаются средствами разработки;
  игроку не требуется открывать их для обычной настройки.
- Меню полностью работает мышью: наведение, щелчок, прокрутка, ползунки,
  назначение клавиш. Клавиатура имеет понятную навигацию и Escape/Enter;
  геймпад сохраняет поддержку. Курсор захватывается только там, где нужен
  обзор/QTE, и корректно освобождается в меню и при потере фокуса.
- Клавиши вызывают отдельные игровые действия: взаимодействие/перезарядка,
  приседание/лёжа, выбор оружия и прочее. Доступны переназначение и режимы
  hold/toggle для подходящих действий; отсутствие залипания проверяется
  при смене контекста, Alt-Tab, возвращении из меню и смене устройства ввода.
- Мышь управляет обзором напрямую, без ограничения скоростью стика.
  Чувствительность, инверсия и ADS настраиваются в игре; одинаковое движение
  проверяется при разных FPS. Глобальную скорость симуляции ради ввода не менять.
- HUD, обучение и QTE показывают актуальные назначенные клавиши/кнопки
  выбранного устройства, включая русский перевод. Все обязательные действия
  кампании выполнимы клавиатурой и мышью; подсказки соответствуют реальному вводу.
- Настройки имеют единое состояние, понятные применение/отмену и сброс.
  Опасная смена видеорежима предусматривает подтверждение с автоматическим
  откатом. Проверять сохранение после полного выхода, menu/Continue и перехода
  между миссиями; одноразовые диагностические CLI-флаги не портят выбор игрока.
- Внешний setup/импорт своей копии допустим как первоначальная подготовка.
  Обычные запуск, продолжение, выбор миссии и настройки проходят в игре.
  Публичная сборка не требует знания отладочных F-клавиш.

Приёмка PC-интеграции: игрок запускает игру, продолжает checkpoint, меняет
настройки и раскладку, проходит меню и игровые взаимодействия только мышью и
клавиатурой, выходит и возвращается с сохранённым выбором — без отладочного UI.
Это целевой результат, а не утверждение о текущей готовности. Активная работа
по огонькам/звуку и проверке кампании сохраняет приоритет; PC-страницы и ввод

## Цель и технические ограничения

Оригинальная одиночная кампания Xbox 360 работает как самостоятельное Windows
x64 приложение: статическая рекомпиляция PPC → C++ → x64, оригинальный движок
и ресурсы принадлежащей пользователю копии. Сохраняем игровую логику, физику,
анимации, графику, звук и сценарии. Интерпретатор, JIT или процесс эмулятора
не становятся backend итогового приложения. Multiplayer вне начального объёма.

Основа — ReXGlue 0.10.0, commit
`c94f5ebdcb3c9d1a460ca48e04f9758448f8d518`, официальный Xenos GPU plugin
с проверяемыми локальными исправлениями совместимости. Используем API исходников
этой версии и фактический CLI `--help`. XenonRecomp/XenosRecomp — возможные
альтернативы только при установленной технической необходимости. CoD3Recomp
служит исследовательским ориентиром; развитие нашего порта не зависит от
ожидания его автора. Заимствование исходников требует проверки лицензии.

VS Code подходит как редактор; необходимые MSVC и Windows SDK предоставляют
установленные Visual Studio Build Tools. Полная IDE не является обязательной.
Xenia может быть эталоном Xbox 360 для локального сравнения. Присланные кадры
RPCS3 помогают сравнить внешний вид, но не доказывают семантику GPU Xbox 360.

Остальные checkpoint и сохранения переходов кампании проверяются по мере
прохождения. Доказательства: [SAVES.md](SAVES.md).

1. Продолжить первую миссию после участка с самолётом. Targets 0x823C1F68
   после грузовика и 0x82498BD0 в бою проверены в Ghidra и зарегистрированы;
   пользователь подтвердил прохождение обоих участков после исправлений.
   Повтор на том же участке выявил новый target 0x891A7A30 в Saint-Lo;
   сначала устранить отсутствие регистрации и повторно проверить бой.
   Следующие вылеты исследовать по оригинальным инструкциям и конкретному логу.
2. Проверить оставшиеся действия и сценарии. Проверить стрельбу, прицеливание,
   перезарядку, гранаты, переходы заданий, коллизии и исходные сценарии.
   Отдельно проверить боевые AI, попадания, урон, смерть и повтор checkpoint.
3. Проверить завершение Saint-Lo и запрос следующего модуля оригинальным
   движком. Зафиксировать guest path, порядок выгрузки и поведение сценариев.
   Следующий уровень выбирать по этому свидетельству, а не по предположению.
4. Проверить checkpoint, выход в меню и продолжение после перезапуска EXE.
   Пройденный участок без восстановления сохранения не закрывает эту проверку.

Критерий выхода из этого этапа: воспроизводимо пройти обучение, поездку и
первый бой, затем получить реальный переход следующей миссии либо точный
следующий блокер с логом. Точечная правка травы уже дала вертикальную траву
без длинных полос в проверенных ракурсах; новые графические дефекты устранять
по отдельным captures, сохраняя растительность.

## Подключение кампании

1. Поддерживать inventory по magic XEX, SHA-256 и сопоставлению manifest с
   оригинальными guest paths. Текущий аудит: 15 SP images, подключён Saint-Lo.
   См. [CAMPAIGN_READINESS.md](CAMPAIGN_READINESS.md).
2. Для следующего реально запрошенного модуля провести отдельный анализ,
   строгую генерацию и сборку native DLL. Ручные границы и coroutine hooks
   проверять на его собственных инструкциях и SHA-256. Не переносить offsets
   из MP TU3 или Saint-Lo без проверки.
3. Проверить штатные SDK LoadUserModule/UnloadUserModule и FunctionDispatcher
   в настоящем переходе. Все 15 образов имеют preferred base `0x89000000`:
   освобождение старых регистраций, thunks и живых continuations должно быть
   согласовано с исходным жизненным циклом. Изученный API не заменяет этот тест.
4. Повторить процесс для оставшихся модулей. Вести таблицу для каждой миссии:
   анализ → codegen → build → загрузка → прохождение → checkpoint → переход.
   Закрыть M7 только после полного прохождения, включая финальные переходы.

## Совместимость основных систем

Проверять системы по мере появления в реальном прохождении; дефекты, мешающие
продолжению, имеют приоритет над добавлением следующих уровней.

| Система | Работа и необходимая проверка |
|---|---|
| PPC/runtime | ABI, endian, FPU/VMX128, стек, tail calls, indirect calls, потоки и timing; каждый missing import имеет caller, контракт и осмысленную реализацию |
| Сценарии | Frame/timed/condition/event waits, сохранение PPC и host frames, освобождение fibers, переходы задач и модулей |
| VFS/ресурсы | Оригинальные пути, регистр имён, структура, сигнатуры и зависимости; сохранить исходный loader, не предполагать форматы CoD4 |
| Графика | Buffers, texture tiling/swizzle, shaders, depth/EDRAM/present; сравнивать GPU captures и живой кадр, ограничивать исправление доказанной областью |
| Ввод | Клавиатура/мышь/XInput, чувствительность, движение/прицеливание, переключение устройств, меню и gameplay |
| Звук/видео | Реальные codecs/events, синхронизация, голоса/музыка/эффекты, длительные сцены; audio callback не доказывает правильный звук |
| Gameplay | Оружие, анимации, физика/коллизии, AI, урон, scripted sequences, транспорт и цели миссий |
| Сохранения | Checkpoints, повтор после смерти, рестарт миссии, продолжение после закрытия процесса, переходы кампании |

перенос чужого кода не сделан. Порядок внедрения:

1. **M6, сейчас:** debug selector с перечнем оригинальных SP XEX, проверкой
   доступной native DLL и отдельными сохранениями на миссию. Запуск через
   штатный devmap, без изменения пользовательского campaign save. Не выводить
   «доступна», пока модуль не подключён, не собран и не задан проверенный map ID.

## Производительность и выпуск

После базового In-Game результата профилировать воспроизводимые игровые сцены:
CPU/GPU frame time, рабочие потоки, syscalls, ожидания и загрузку ресурсов.
Сначала исправлять измеренные причины. 60 FPS — целевой результат, который
требует проверки на указанном оборудовании; скорость одного лагеря не
характеризует кампанию. Для измерений использовать оптимизированную сборку
с символами, а не Debug -O0.

Перед M8: проверить долгие игровые сессии, настройки изображения/звука/ввода,
ошибки отсутствующих ресурсов, понятный запуск и импорт собственной копии,
воспроизводимость сборки и зависимости/лицензии распространяемого пакета.
Оригинальные и производные игровые данные/код не помещать в Git и remote builds.
Распространяемый состав определить после отдельной проверки; не включать
закрытые Xbox SDK, игровые assets, ключи и приватные диагностические материалы.

## Рабочий цикл и команды

Для каждого существенного исправления: точное воспроизведение → первая неверная
операция → проверка оригинального кода/SDK → минимальное исправление → подходящие
tests → strict codegen → native build → реальный повтор проблемного участка.
Фиксировать команды, ошибки, область проверки и следующий блокер в документах.
Generated functions не редактировать вручную. `--force` допустим только для
диагностики и не является критерием готовности; strict запуск использует
`--ignore-stamp`.

```powershell
./tools/Check-Environment.ps1
./tools/Build.ps1 -Stage Tests
./tools/Build.ps1 -Stage Analyze
./tools/Build.ps1 -Stage Codegen
./tools/Build.ps1 -Stage Build
./tools/Run-Native.ps1 -Seconds 0 -Interactive
./tools/Inspect-Target.ps1 -Address 0x823C1F68
```

Ручные проверки начинаются из обычного меню, чтобы продолжать с checkpoint.
Запускать одно окно. -FirstMission применять только для проверки новой миссии,
когда это действительно нужно; пользователь предпочитает продолжение сохранения.

Старые примеры init из исходного промпта заменены командами v0.10.0:
`--project-name`, `--xex-path`, `--project-root`, `cod3pc_manifest.toml`.
Повторно init поверх проекта не выполнять; точный bootstrap приведён в
[BUILDING.md](BUILDING.md). Восемь текущих parser/coverage/native tests
проверяют инструменты и отдельные runtime свойства, а не проходимость кампании.

Продолжать техническую работу автономно в согласованном объёме. Ручные игровые
проверки запрашивать, когда они нужны для подтверждения поведения. Новые
системные разрешения, отсутствующие assets и принципиальная смена подхода
обсуждаются отдельно. Сроки следующего этапа определяются найденными дефектами,
а готовность — перечисленными проверками.
